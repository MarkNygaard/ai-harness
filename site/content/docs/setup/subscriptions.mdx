**Settings → Subscriptions** holds the accounts your agents run on. Values are
entered there, encrypted at rest in Postgres, and injected into the agent
environment at run time. They never go into cluster secrets, and they are
write-only: nothing is shown back to you after saving.

Which agent uses which account is set separately, on **Settings → Agents**.
GitHub and Linear are not here either; they live under
**Settings → Integrations**.

## What each account backs

| Account | Connected by | Backs |
| --- | --- | --- |
| **Claude** | Pasting an OAuth token, or the full `~/.claude/.credentials.json` | Claude Code nodes |
| **ChatGPT** | **Connect ChatGPT**, an OAuth flow | `openai-codex/*` models on Pi |
| **Kimi-for-Coding** | **Connect Kimi**, a device login | `kimi-code/*` models on Pi |
| **Cursor** | Pasting an API key | `cursor-agent` nodes |

Moonshot's per-token API is separate from the Kimi subscription. It is an API
key rather than a login, and covers `moonshotai/*` models.

## Several Claude accounts

You can connect more than one Claude subscription. Under the Claude card,
**Add a Claude account** gives each one a name and its own credential. Each
account gets its own Claude Code config folder, so their logins, settings and
sessions never mix.

With two or more connected, each run picks an account when it starts:

- **The most room left wins.** The harness reads each account's usage, the
  share used of its 5-hour and weekly windows, and takes the tighter of the
  two. Those shares are relative to the account's own plan, so they are
  weighted by the plan's size: half of a Max 20x is more than an empty Pro.
- **The plan is read from the credential.** Pro counts as 1, Max 5x as 5 and
  Max 20x as 20. Set a size by hand on the account only if it is missing or
  wrong.
- **Busy accounts count less.** Runs already using an account count against
  it until its usage catches up, so runs that start together spread out.
- **A run stays on its account.** Claude keeps a run's conversations in that
  account's folder, so every Claude step of the run uses it.
- **At a usage limit, the run moves on.** The step that hit the limit starts
  again on the account with the most room. It starts fresh, because its
  conversation stays with the old account. Only when every account is at its
  limit does the run wait for a reset, as it would with one account.

The dashboard shows a usage card per account, and the run's activity says which
account each Claude step used.

Check your provider's terms before pooling subscriptions. Seats on a Team or
Enterprise plan are meant for this; several personal Pro or Max accounts used
to get past each one's limits may not be.

## Cursor bills its own models differently from the rest

Read this before a workflow spends a week on the wrong model.

The plan covers Cursor's own models, Composer and Grok. It does not cover
Claude, GPT and Gemini reached through Cursor. Those draw from a separate pool,
charged at the model's API price. Both kinds work with the same API key and
neither asks for another one, which is why the difference is easy to miss.

The editor marks it. A model the subscription does not cover carries an
**API price** badge in the model dropdown, and the chosen one says so under the
field. Nothing is blocked. Picking a metered model is a decision, not an error.

The same model can fall on either side depending on which agent reaches it.
`sonnet` on Claude Code is the Claude subscription. `sonnet` on the Anthropic
API provider is a per-token bill.

## Connect ChatGPT signs Pi in

Worth knowing, because it saves a step people often go looking for.

**Connect ChatGPT** hands the ChatGPT tokens to Pi, so `pi` nodes can run
`openai-codex/*` models. The server does this through `omp auth-broker import`
during the connect, and the request fails loudly if it does not take. A
successful connect means Pi is signed in.

<Callout>
There is no separate login for Pi. If you find a runbook telling you to open a
terminal on the container and run `omp /login`, it predates this and is no
longer needed.
</Callout>

### Addressing OpenAI models on Pi

On the `pi` provider the model id **must** be namespace-qualified:

```yaml
provider: pi
model: openai-codex/gpt-5.6-sol
```

A bare name gets mis-prefixed to `kimi-code/...` and fails. To see which models
your account actually exposes, run `omp` on the container and then `/model`.

<Callout type="warn">
A ChatGPT subscription exposes the general models, not the `-codex` variants.
Those need API-key authentication, which the harness does not offer.
</Callout>

## Subscriptions and API keys behave differently

A subscription login is an OAuth token pair that refreshes itself. An API key is
a static string. That difference produces two behaviours worth knowing about
before you debug something.

**Stored credentials are seeded, not overwritten.** Claude Code rotates its
refresh token in place on disk. If the harness wrote its
stored copy back on every run, it would re-present a token that has already been
spent, and authentication would start failing within a day. So that file is
written only when missing. Pasting a fresh credential still takes effect
immediately.

**The Claude subscription token is refreshed per run.** Its access token lives
about eight hours and the CLI does not reliably refresh it in headless
subscription runs, so an idle gap would otherwise fail a run partway through.
The harness refreshes it at the start of each real run instead.

## Per project, with a global fallback

Credentials can be set per project as well as globally. A project without its
own falls back to the global one, which is usually what you want: one set of
model accounts, and a per-project GitHub credential so pull requests are opened
by the right identity.

## When a run fails to authenticate

Reconnect from **Settings → Subscriptions** first. It re-runs every half of the
flow, which is cheaper than working out which one went stale.

The usual cause is a replaced data volume. Subscription credentials are seeded
onto it, so a fresh volume starts empty even though the credential is still in
Postgres. A reconnect repairs it.
