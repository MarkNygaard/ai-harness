title: "Sentry"
description: "Let agents read production errors in Sentry: a read-only token, the organization, and each project's Sentry project."
---

With Sentry connected, an agent working on a bug can read the error itself:
the stack trace, how often it happens, which release introduced it. That
saves it guessing from the issue text. Agents use Sentry's own MCP server.

Connect it on **Settings → Integrations → Sentry**.

## The token

Create a token with **read access only**. There are two ways, and one way that
won't work:

- **A custom integration (recommended).** In Sentry, go to Settings → Custom
  Integrations → Create New Integration → **Internal Integration**. Give it
  **Read** on Project, Team, Organization and Issue & Event, and nothing else.
  Then copy its token. It belongs to the organization, so it keeps working when
  the person who made it leaves, and its permissions can be changed later.
- **A personal token.** Settings → **Personal Tokens**, with the same four set
  to Read. It's tied to your account: it stops working if you leave the
  organization, and its scopes can't be changed afterwards.
- **Organization Tokens won't work.** They're for CI and source-map uploads,
  and can't read issues or events.

The harness also runs Sentry's server with only its read-only tools, so agents
can't resolve, assign or change anything. A read-only token makes that hold even
if something upstream changes.

Also enter the **organization slug**, the part after
`sentry.io/organizations/` in the URL. Agents are limited to that organization.

## Each project's Sentry project

Under **Settings → Projects**, a project can name the **Sentry project** its
errors are reported under. Agents looking at Sentry for that project are then
limited to it, which keeps searches relevant and quick. Without one they can
look across the organization.

## Where agents use it

- **Workflow steps that ask for it** with `mcp: [sentry]`. See
  [External tools](/docs/workflows/authoring#external-tools-mcp).
- **The chat**, for questions like "what started erroring after yesterday's
  deploy?"

The token is never written to a file. It's handed to Sentry's server through
the environment of the step or chat that uses it.

A `bash` step that calls Sentry's API itself can read the same values as
`$HARNESS_SENTRY_TOKEN`, `$HARNESS_SENTRY_ORG` and `$HARNESS_SENTRY_PROJECT`.
They're deliberately not called `SENTRY_AUTH_TOKEN` and so on: those are what
Sentry's build tooling reads to upload source maps, and a project's build would
try an upload with this read-only token. Where you can, prefer `mcp: [sentry]`
on an agent step over hand-written `curl`.

Sentry's server can also run Seer, Sentry's AI debugger, but that's off here,
because it uses your Sentry quota. Its natural-language search is off too:
otherwise it would call OpenAI or Anthropic with keys the harness holds.
Searches use Sentry's query syntax instead, which agents handle well.
