---
title: "Sentry"
description: "Connect Sentry once, read-only, so workflow scripts and the chat can look up production errors without ever holding the token."
---

With Sentry connected, the harness can read your production errors: the stack
trace, how often an error happens, which release introduced it. A workflow's
`bash` or `script` steps read it with
[`harness sentry`](/docs/operating/cli#harness-sentry), and the chat reads it
with its own tools.

Connect it on **Settings → Integrations → Sentry**.

Sentry is an **integration**: the harness holds the token and makes each read
itself, and nothing it starts ever gets the token. If you also want agent
steps to use Sentry's own MCP server as tools, add it under
[MCP servers](/docs/setup/mcp-servers#sentry-and-grafana-as-mcp-servers).
That's a separate setup.

## The token

Create a token with **read access only**. There are two ways, and one way that
won't work:

- **A custom integration (recommended).** In Sentry, go to Settings → Custom
  Integrations → Create New Integration → **Internal Integration**. Give it
  **Read** on Project, Team, Organization and Issue & Event, and nothing else.
  Then copy its token. It belongs to the organization, so it keeps working when
  the person who made it leaves, and its permissions can be changed later.
- **A personal token.** Settings → **Personal Tokens**, with the same four set
  to Read. It's tied to your account: it stops working if you leave the
  organization, and its scopes can't be changed afterwards.
- **Organization Tokens won't work.** They're for CI and source-map uploads,
  and can't read issues or events.

Also enter the **organization slug**, the part after
`sentry.io/organizations/` in the URL. Every read is limited to that
organization.

Leave **Sentry URL** empty for sentry.io. Set it for a self-hosted Sentry, or
for a region such as `https://de.sentry.io`.

## Each project's Sentry project

Under **Settings → Projects**, a project can name the **Sentry project** its
errors are reported under. Issue searches for that project are then limited to
it (`harness sentry issues` and the chat's search), unless a search names
another project. Without one, searches cover the organization.

## What can be read

Only reads, and only in the connected organization: issues, their events
(with stack traces) and tags, events, traces, releases and the list of
projects. Anything else, such as resolving or assigning an issue, is refused
by the harness, and a read-only token refuses it again.

```bash
harness sentry issues --query "is:unresolved level:error" --period 24h
harness sentry issue 4512 --latest-event
```

The chat gets the same reads, for questions like "what started erroring after
yesterday's deploy?"
