An **epic** is a Linear issue with sub-issues. Delegate it to the harness and it
builds the sub-issues one at a time, each on a shared branch, each graded
against its own description before the next begins. The default branch sees the
feature once, finished, as a single pull request.

This page is about **setting that up**. For writing the workflows themselves see
[Authoring workflows](/docs/workflows/authoring); for connecting a Linear
account see [Connecting Linear](/docs/setup/linear).

## When an epic is the wrong shape

Most work is not an epic. `task` already explores, plans and decomposes inside
one run — its plan step routinely produces ten numbered tasks with exact file
paths, executed by a cheap model. Splitting the same work across sub-issues
multiplies the cost rather than the quality: **each piece is a full pipeline**
(explore, plan, implement, self-review, verify) **plus a grade**.

An epic earns that when one of two things is true:

1. **The work exceeds one run's coherence** — explore, plan, implement and review
   share a single context, and past some size the plan stops being specific
   enough to execute cheaply.
2. **Later pieces depend on earlier ones being *right*, not merely done** — each
   piece is graded with fresh context before the next starts, where a single
   run's review sees the finished diff and a wrong early step has already
   propagated.

The test: *if you cannot say what would break if two pieces were built in the
other order, it does not need to be an epic.*

Independent work is a poor fit even when it is large. Several documentation
pages, or unrelated fixes across a repo, gain nothing — the branch exists so
piece N+1 starts from a tree containing 1..N, and independent work pays that
sequential cost for no benefit. File those as separate issues and let them run
in parallel.

Good epic: a frontend where component B imports component A. Poor epic: a docs
set, or three unrelated bug fixes.

## How `task` runs an epic

The bundled [`task`](/docs/workflows/bundled#task) workflow runs an epic in its
own graph. One [trigger](/docs/triggers), Todo → `task`, is the whole setup:

```
Todo  →  task
           ├ an epic   → creates epic/<EPIC>, moves the first piece to Todo
           ├ a piece   → builds it on epic/<EPIC>, grades it, merges it,
           │             moves it to Done, moves the next piece to Todo
           │             (after the last: one PR epic/<EPIC> → default branch,
           │              and the epic to In Review)
           └ a task    → builds it as usual
```

The first step reads the issue and decides which it is:

- **An epic** is an issue with sub-issues and no parent. The run creates the
  branch `epic/<EPIC>` from the base branch and pushes it, then moves the first
  sub-issue that hasn't begun to the column pieces start in. It comments on the
  epic to say which piece it started. It builds nothing itself.
- **A piece** is a sub-issue whose epic has started, which is when
  `epic/<EPIC>` exists. Its run is based on the epic branch, so piece N+1
  starts from a tree that already contains 1..N. It goes through the pipeline,
  then a grade with fresh context judges it against its own description.
- **An ordinary issue** goes through the pipeline and opens a pull request
  against the base branch. So does a sub-issue of an epic nobody started.
- **An epic whose pieces have all begun** is skipped: there is nothing to start.

Each piece is its own run with fresh context, started from the board, so an
epic survives a restart and you can follow it on the board.

**The grade comes before the merge.** A piece that falls short gets one round
of fixes and a second grade. When it passes, its pull request is squash-merged
into the epic branch, the piece moves to Done, and the next piece that hasn't
begun moves to the start column. The epic gets a comment with the grade's
summary. The list of pieces is read again at that point, so a piece added or
reordered while the last one was building is respected.

**After the last piece**, the run opens `epic/<EPIC>` as one pull request
against the default branch and moves the epic to In Review. That pull request is
the first review of the whole change. Merge it as you would any other: approve
it, and move the epic to Ready for merge if a
[`task-merge`](/docs/workflows/bundled#task-merge) trigger watches that column.

**Pieces merge without a person approving them.** That's safe only if your
repository doesn't require reviews on `epic/*` branches. The grade is the check
on each piece, and the finished feature is reviewed once, as the epic's own
pull request.

## Where issues go

Optional project env vars override the columns:

| env var | what it sets | default |
|---|---|---|
| `EPIC_READY_STATE` | where a piece starts | the column the epic was picked up from, else Todo |
| `EPIC_REVIEW_STATE` | where the finished epic goes | In Review |
| `EPIC_BLOCKED_STATE` | where the epic goes when a piece is stuck | the epic stays where it is |

Whatever column pieces start in, something must start `task` from it. With the
default, that is the same trigger that picked up the epic.

You can also bind `task` under a project's Linear setup instead of a trigger.
Leave the binding's status map empty, so the poller and the workflow's own
`linear:` steps don't both move the issue.

## Writing the epic

**Put the sub-issues in build order on the epic.** Pieces build in the order
of the epic's own sub-issue list, top first. Linear shows that order when the
list's display options sort it manually. Other sorts, such as by priority,
show something else. Drag the sub-issues there until the first piece is on top.
Their place on the board doesn't matter.

**Delegate every sub-issue and the epic**, then put the epic in the build
column. The harness cannot delegate an issue to itself, so a piece nobody
delegated is never picked up no matter which column it reaches.

**Give each piece its own acceptance criteria.** The grade judges a piece
against its own description and nothing else — not against what it would have
built, and not against work the criteria leave to a later piece. Vague criteria
produce a pass on work that does not hold up. Criteria that overlap the next
piece produce a failure for something not yet due.

## When an epic stops

A piece stops for a person in two cases, and the epic waits until someone acts:

- **It failed its grade twice**, once after a round of fixes. Its pull request
  stays open and the piece moves to In Review. The epic and the piece both get
  a comment with what the second grade found, and the epic moves to
  `EPIC_BLOCKED_STATE` if you set one.
- **GitHub would not merge it** into the epic branch: a branch rule, a conflict
  or a failing check. The piece moves to In Review and the epic gets a comment
  with GitHub's reason.

Either way, merge the piece's pull request by hand, move the piece to Done and
the next piece to the start column, and the epic carries on.

Otherwise:

- **A piece sits in the start column and nothing happens** — nothing starts
  `task` from that column, or the piece was never delegated. Check the trigger,
  or `EPIC_READY_STATE` if you set it, and delegate the piece.
- **The epic sits in the build column and nothing happens** — it needs
  sub-issues. An issue without them is built as an ordinary issue. An epic whose
  pieces have all begun is skipped on purpose.
- **A sub-issue was built against the default branch** — its epic had not
  started, because `epic/<EPIC>` did not exist yet. Start the epic first.

## With `linear-epic-supervise`

The bundled [`linear-epic-supervise`](/docs/workflows/bundled#linear-epic-supervise)
workflow grades a merged piece, then advances the next one or files a
corrective sub-issue. `task` does not use it, and nothing wires it up for you.
It is for a custom setup in which separate project bindings build and merge the
pieces, with the supervisor bound to the column a merged piece lands in. Once a
supervisor binding exists on the team, the poller sends an epic to it rather
than to a build workflow that does not run epics itself, and builds each piece
on `epic/<ID>`. The
binding form's **Ready (epic piece)** and **Ready (finished epic)** fields, and
the **Wiring** panel under the binding list (`linear_check` over MCP), exist for
setups like that.
