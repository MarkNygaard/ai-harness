The harness serves MCP over HTTP, so an MCP-connected assistant can trigger runs
and author workflows against your cluster.

## Two transports

The harness speaks MCP two ways, and they do not expose the same thing.

| | **HTTP endpoint** | **`harness mcp-server`** |
| --- | --- | --- |
| How | The running server, at `/mcp` | The binary locally, over stdio |
| Tools | Runs, Linear **and** authoring | Authoring (`workflow_*`) only |
| Auth | MCP key or personal access token | `HARNESS_TOKEN` in the client's env |
| Needs | Network reach to the harness | The binary on your machine |

**Use the HTTP endpoint** unless you have a reason not to. It is the one that
can actually start runs.

The stdio mode exists for clients that cannot do authenticated HTTP MCP. It
proxies the `workflow_*` tools to the cluster's global authoring API, so you can
write workflows through it, but **it cannot trigger or inspect runs.**

```json
{
  "mcpServers": {
    "harness-authoring": {
      "command": "harness",
      "args": ["mcp-server"],
      "env": {
        "HARNESS_REMOTE_URL": "https://harness.example.com",
        "HARNESS_TOKEN": "<your token>"
      }
    }
  }
}
```

## Connecting

The dashboard builds the configuration for you: **Settings → Editor connection**
shows the endpoint, the MCP key, and a ready-to-paste snippet for Claude Code,
Cursor, VS Code and Claude Desktop.

The server generates the key on first start and stores it encrypted, so there
is nothing to put in your deployment manifest.

```bash
claude mcp add --transport http harness https://<your-harness-host>/mcp \
  --header "Authorization: Bearer <your MCP key>"
```

Or for an editor that reads a config file:

```json
{
  "mcpServers": {
    "harness": {
      "type": "http",
      "url": "https://<your-harness-host>/mcp",
      "headers": { "Authorization": "Bearer <your MCP key>" }
    }
  }
}
```

<Callout type="warn">
Keep the key out of a project's `.mcp.json`. That file is normally committed and
this configuration carries a secret. Use the `claude mcp add` command above,
which writes to your user configuration, or your editor's user-level config.
Keys are prefixed `hrn_mcp_` so secret scanners can catch one that slips into a
repository.
</Callout>

With sign-in enabled, mint a **personal access token** on that page instead of
using the shared key. A run triggered from your editor is then attributed to
you, and revoking one person's access does not disturb anybody else's editor.

## Tools

### Runs

| Tool | What it does |
| --- | --- |
| `run_trigger` | Start a run: project, workflow, task, optional model override. |
| `run_trigger_pair` | Start the **same task twice** on different models. The A/B comparison, feeding `judge-ab`. |
| `run_list` | Recent runs and their states. |
| `run_status` | One run's progress, node by node. |
| `run_findings` | What the review passes found. |
| `run_activity_errors` | Errors recorded during a run. The first place to look when one fails. |
| `run_linear_claim` | Claim a Linear issue for a run. |

### Linear

| Tool | What it does |
| --- | --- |
| `linear_states` | The workflow states available in a team. |
| `linear_bindings` | Which columns are bound to which workflows. |
| `linear_check` | Diagnose a binding. Usually the answer to "why did nothing happen?". |

### Workflow authoring

| Tool | What it does |
| --- | --- |
| `workflow_list` | Workflows visible to a project. |
| `workflow_get` | One workflow's YAML. |
| `workflow_create` | Create a new workflow. |
| `workflow_save` | Save a full workflow document. |
| `workflow_validate` | Validate without saving. |
| `workflow_delete` | Remove a workflow. |
| `workflow_set_node` | Add or update a single node. |
| `workflow_remove_node` | Remove a node. |
| `workflow_connect` | Wire one node's output into another. |
| `workflow_set_ui` | Set the visual editor's layout metadata. |
| `workflow_catalog` | The node-type catalog. |
| `workflow_models` | Which providers and models are available. |

The node-level tools exist so an assistant can edit a workflow incrementally
without rewriting the whole document, and so a malformed edit fails on one node
rather than replacing a working DAG with a broken one. Validate before saving.

## A/B comparisons

`run_trigger_pair` starts one task on two arms with different models, holding
everything else constant. Feed both results to the
[`judge-ab`](/docs/workflows/bundled#judge-ab) workflow to get a scored verdict
based on the actual diffs rather than on the models' own summaries of their
work.
