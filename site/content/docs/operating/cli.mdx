The same `harness` binary serves the control plane and runs workflows locally.
`--config <path>` is global to every subcommand.

## `harness serve`

Start the control plane, meaning the HTTP API and the bundled dashboard.

```bash
harness serve --transport http --port 9800 --project-root /var/lib/harness/projects
```

| Flag | Purpose |
| --- | --- |
| `--transport` | Transport mode; defaults to the config value, else `http`. |
| `--port` | HTTP port (http/websocket transports). |
| `--project-root` | Project root used by server-side scans (GC, health). |
| `--project NAME=PATH` | Register a named project at startup. Repeatable. |
| `--default-project` | Which registered project `--project` flags default to. |

## `harness run`

Execute a workflow DAG locally and print a per-node summary. This is the fastest
way to iterate on YAML.

```bash
# bundled default pipeline, echo agent, current directory
harness run

# a named workflow with real agents, in a throwaway worktree
harness run task --args "add a health endpoint" --real --worktree
```

The positional argument is a `.yaml` path **or** a bundled/project workflow
name; omit it for the bundled standard pipeline.

| Flag | Default | Purpose |
| --- | --- | --- |
| `--workspace` | current directory | Directory to run against. |
| `--base-branch` | `main` | Exposed as `$BASE_BRANCH`; used for worktree isolation. |
| `--args` | `""` | Free-form text exposed as `$ARGUMENTS` / `$USER_MESSAGE`. |
| `--real` | off | Use real agents instead of the built-in echo agent. |
| `--sandbox` | `danger-full-access` | Sandbox mode for real CLI agents. |
| `--worktree` | off | Run inside an isolated git worktree, removed afterwards. |
| `--database-url` | `$HARNESS_DATABASE_URL` | Persist the run to Postgres. |

<Callout>
Without `--real`, nodes run against a built-in echo agent. Shape, gating and
`$node.output` wiring all run for free. Check a DAG behaves before spending
tokens on it.
</Callout>

## `harness status`

Live server health, queue depth and workflow runtime state.

```bash
harness status --json
```

| Flag | Purpose |
| --- | --- |
| `--url` | Server base URL; defaults to `server.http_addr` from config. |
| `--project-id` | Filter the runtime tree to one project. |
| `--runtime-limit` | Max workflow rows requested (default 20). |
| `--json` | Raw combined JSON instead of the text summary. |

## `harness exec`

Execute a single prompt non-interactively, without a workflow.

```bash
harness exec "summarise the recent changes" --project . --agent auto
```

Notable flags: `--agent` (default `auto`), `--model`, `--sandbox-mode`
(default `workspace-write`), `--output-file`, and the actor allow-lists
`--allow-users` / `--allow-bots` / `--actor` used when the caller is a GitHub
identity. `--drop-sudo` defaults on and refuses to execute from a root context.

## `harness linear`

Write to Linear **as the harness app**. These are the operations workflow steps
use; they are documented because a workflow author calls them from a `bash`
node.

| Subcommand | What it does |
| --- | --- |
| `create-issue` | File a standalone issue in a team, given by key or name. For handing a result to people, such as a scheduled report. |
| `create-sub-issue` | File a sub-issue under an epic, in the epic's own team. |
| `move-state` | Move an issue to a workflow state. `--cycle` sets its cycle in the same update. |
| `update` | Replace an issue's description, set its cycle, or both. Nothing else changes. See [Refining issues](/docs/workflows/authoring#refining-issues). |
| `comment` | Comment on an issue. The epic ledger. |
| `comments` | Print every comment on an issue as JSON, oldest first. Read-only. |
| `issue` | Print one issue's team, state, parent, labels, cycle, and what blocks it or it blocks (`blocked_by`, `blocks`) as JSON. |
| `issues` | Print a team's issues as JSON, filtered by status, assignee, labels and cycle. Read-only. See [Triaging issues](/docs/workflows/authoring#triaging-issues). |
| `label` | Add or remove an issue's labels by name. Existing labels only. |
| `children` | Print an epic's sub-issues as JSON, in board order. |
| `release` | Give up an issue so the poller stops offering it. |
| `epic-review-state` | The state a finished epic moves to, per its binding. |
| `ready-state` | The state a piece must reach to be built. |

**No subcommand names a workspace or a token.** The run's grant says which
project it speaks for and the server resolves that to a connection exactly as
the poller would, so an epic's sub-issues cannot land in a workspace its runs
never watch, and a run cannot write as somebody else.

Bodies with newlines go through `--description-file` / `--body-file` rather than
`--description` / `--body`, which is the usual case since acceptance criteria
are written to an artifact by a planning step.

## `harness grafana`

Read the connected Grafana from a `bash` or `script` step. Needs
[Grafana connected](/docs/setup/grafana).

```bash
# Instant query, at a time or now
harness grafana loki 'sum(count_over_time({job="web-vitals"} [1d]))' --time 1795600000
# Range query
harness grafana prometheus 'rate(http_requests_total[5m])' \
  --start 2026-11-20T00:00:00Z --end 2026-11-27T00:00:00Z --step 1h
# Any path the proxy allows, with query parameters
harness grafana get api/datasources/name/Loki
harness grafana get api/datasources/proxy/uid/<uid>/loki/api/v1/labels -p since=24h
```

`loki` and `prometheus` find the datasource themselves (the default one of its
kind, or `--datasource <name or uid>`) and print the datasource's JSON answer.
`--limit` caps a Loki query's log lines.

The step never holds the Grafana token. The command asks the server with the
run's grant, and the server adds the token. Only reads go through: datasource
lookups, Loki and Prometheus queries, labels and series, and dashboard search
and reads. Anything else is refused.

A script can call the same proxy directly, which suits many queries in one
step:

```ts
const r = await fetch(
  `${process.env.HARNESS_RUN_URL}/api/run/grafana/api/datasources`,
  { headers: { Authorization: `Bearer ${process.env.HARNESS_RUN_TOKEN}` } },
);
```

## `harness s3`

Upload a file a workflow step produced to the project's S3 folder. Needs
[S3 connected](/docs/setup/s3).

```bash
harness s3 upload "$ARTIFACTS_DIR/production.tar.gz"
harness s3 upload report.pdf --name reports/weekly.pdf
```

The run never holds the access key. The server signs a short-lived upload link
for that one object under the project's folder, and the file goes straight to
S3. Prints the object as JSON.

## `harness title`

Rename the run a step belongs to. A webhook or a schedule names its run when it
fires, before the run has found out what it will work on. A step that knows can
say so, and the runs list shows the new name.

```bash
harness title "Resolve conflicts: #1182, #1171"
```

One line, at most 200 characters. The run is the one whose grant the step
holds, so a step can only rename its own run. The name stays when the run
finishes.

## `harness admin`

Break-glass account recovery.

```bash
harness admin create --email you@example.com --password '<password>'
```

Creates an administrator, or promotes an existing account and sets its password.

<Callout type="warn">
Signing in can be turned on but **never off**. Nothing can turn it off. This
command exists so that one-way door is a safeguard rather than a trap. It
requires a shell on the server, which is the correct bar.
</Callout>

## Others

- `harness mcp-server` speaks MCP over stdio, as opposed to the server's HTTP
  endpoint.
- `harness pr` implements an issue and manages the review loop.
- `harness rule` runs the rule engine.
- `harness execpolicy` runs the Starlark exec-policy commands.
- `harness version` prints the version.
