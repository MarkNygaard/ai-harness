The harness does not talk to model APIs directly. It drives **agent CLIs** as
subprocesses: it builds the prompt and manages the lifecycle, and the agent
decides how to execute. Each one needs its own binary on `PATH` and its own
credentials.

## Providers

A node's `provider` selects the agent. Several names route to the same one:

| `provider` | Agent | Notes |
| --- | --- | --- |
| `claude` | Claude Code CLI | Run headless. The default for planning and review steps in the bundled workflows. |
| `openai-codex` | Codex | Also reachable through Pi on a ChatGPT subscription. |
| `pi`, `kimi`, `omp` | Pi | Three aliases for one agent. Pi's CLI binary is named `omp`, which is why that spelling is accepted. |
| `cursor` | `cursor-agent` | Needs the binary on `PATH`. Without it, `cursor` nodes fail to spawn. |

Anything the dispatcher does not recognise falls through to the default agent,
so an unknown provider name falls back instead of failing. Worth knowing when a
node behaves as though its `provider:` were ignored, because it was.

## Credentials

Credentials live on the dashboard's **Credentials** page, encrypted at rest with
`HARNESS_SECRET_KEY`, and can be set per project with a global fallback.

They are not all connected the same way, and the difference matters when you are
setting a harness up:

| Provider | How you connect it | Where it lands |
| --- | --- | --- |
| **Codex** | **Connect Codex** in the dashboard | `~/.codex/auth.json` |
| **Kimi** | **Connect Kimi** in the dashboard, a device login | Pi's `~/.omp/agent/agent.db` |
| **Claude** | Paste an OAuth token or a credentials JSON | `CLAUDE_CODE_OAUTH_TOKEN`, or `~/.claude/.credentials.json` |
| **Moonshot** | Paste an API key | `MOONSHOT_API_KEY` |
| **Cursor** | Paste an API key, or run `cursor-agent login` on the container | `CURSOR_API_KEY`, or `~/.cursor/cli-config.json` |
| **GitHub** | Paste a token | `GH_TOKEN` and `GITHUB_TOKEN` |

All of it is done from the dashboard. Nothing here needs a terminal on the
container.

**Connect Codex** is worth understanding, because one connect covers two
providers. It writes `~/.codex/auth.json` for the `codex` provider *and*
provisions the same ChatGPT tokens into Pi, so `pi` nodes can run
`openai-codex/*` models without a second login. See
[ChatGPT subscription](/docs/operating/chatgpt-subscription).

<Callout>
Two of these seed a file only when it is missing rather than overwriting it each
run. Claude Code and the Codex CLI both rotate their refresh token in place, so
writing the stored copy back on every run re-presents a token that has already
been used, and authentication fails within a day. Pasting a fresh credential
still takes effect immediately.
</Callout>

Control-plane secrets are scrubbed from the processes a run spawns, so an agent
cannot read the database URL or the encryption key out of its own environment.

## Choosing a model per node

`provider`, `model` and `effort` are all per-node. That is the whole point of
the DAG: a workflow can plan with an expensive model at high effort and
implement with a cheap one.

```yaml
- id: create-plan
  provider: claude
  model: opus
  effort: max
  prompt: |
    ...

- id: implement
  provider: kimi
  command: implement-tasks
```

`effort` takes `low` | `medium` | `high` | `xhigh` | `max` and is passed to the
agent CLI. Spend it where judgement matters, on planning and architecture, and
not on mechanical steps.

**Prefer a family alias over a dated model id.** `model: opus` keeps working
when the vendor ships a new version. A pinned id like `claude-opus-4-1-20250805`
freezes the workflow to a model that will eventually be retired, and you will
find out when a run fails rather than when you read the release notes. Pin an
exact version only when you are comparing two of them and need the comparison
held still.

## Why the bundled workflows mix models

In [`idea-to-pr`](/docs/workflows/bundled#idea-to-pr), Claude plans, Kimi
implements, and then **an OpenAI model and a Claude model each review and fix in
turn**.
That is deliberate: a model reviewing its own output tends to agree with it. A
reviewer that did not write the code catches a different class of mistake, which
is why the bundled pipelines pay for a second and third pass rather than looping
the author again.

[`architect`](/docs/workflows/bundled#architect) goes further. Its
behaviour-preservation review will **revert** a change that drifted semantics,
rather than reporting it.

## Comparing models

To find out whether a model change is actually an improvement, run the same task
twice and have a third model judge the diffs:

- `run_trigger_pair` over [MCP](/docs/triggers/mcp) starts both arms with
  everything but the model held constant,
- [`judge-ab`](/docs/workflows/bundled#judge-ab) scores them from the actual
  code change rather than from either model's account of its own work.
