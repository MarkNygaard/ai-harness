title: "ChatGPT subscription"
description: "Run OpenAI models on a ChatGPT Plus or Pro subscription instead of per-token API billing. One connect in the dashboard covers both the Codex CLI and Pi."
---

Workflow nodes can run OpenAI models on a **ChatGPT Plus or Pro subscription**
rather than an API key billed per token.

## Connect it

**Credentials → Connect Codex** in the dashboard. That is the whole setup.

One connect provisions both places the tokens are needed:

- `~/.codex/auth.json`, which the **`codex` provider** uses.
- Pi's own credential store, which the **`pi` provider** uses to run
  `openai-codex/*` models.

The second one is easy to miss and is the reason there is nothing else to do.
The server hands the ChatGPT tokens to Pi through `omp auth-broker import`
during the same connect, and the request fails loudly if that half does not
take, so a successful connect means both are set.

<Callout>
There is no separate login for Pi. If you find a runbook telling you to open a
terminal on the container and run `omp /login`, it predates this and is no
longer needed.
</Callout>

## Model addressing

On the `pi` provider, the model id **must** be namespace-qualified:

```yaml
provider: pi
model: openai-codex/gpt-5.6-sol
```

A bare name would be mis-prefixed to `kimi-code/...` by the `pi` provider and
fail. On the `codex` provider, address the model the way the Codex CLI expects.

To see exactly which models your account exposes, run `omp` on the container and
then `/model`.

<Callout type="warn">
A ChatGPT subscription exposes the general models, not the `-codex` variants.
Those need API-key authentication and the dedicated `codex` provider.
</Callout>

## How it works

The credential is an OAuth token pair, not an API key. Both stores refresh
themselves, and both live on the data volume, so the connect survives restarts.

Token usage, including cache reads, comes back through Pi's own JSON event
stream, so the run overview shows real input, output and cache splits rather
than estimates.

## If a run fails to authenticate

Reconnect from the Credentials page first. That re-runs both halves.

The two stores can drift apart if the data volume was replaced, since the
credential is seeded onto it. A reconnect fixes that, and is cheaper than
working out which half is stale.
