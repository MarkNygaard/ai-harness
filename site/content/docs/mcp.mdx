The harness serves MCP over HTTP, so an assistant you are already talking to can
work against your cluster directly.

It is easy to read MCP as another way to start a run. That is the least of what
it does. **Triggering is the fallback for teams not using Linear.** If your work
already arrives as issues, [delegate them](/docs/setup/linear) and
let the board be the interface.

What MCP is genuinely for is the developer's side of the loop:

- **Writing workflows** without hand-editing YAML and guessing at the schema.
- **Reading what a run did** at the node level, including what the reviewers
  caught and what errored.
- **Turning that into rules**, which is the part that compounds.

## The loop that makes runs better

[Project rules](/docs/project-rules) makes the case that writing the same review
comment twice means you have found a missing rule. MCP is how you find them
without reading a hundred diffs by hand.

From your editor, ask the assistant to look at the last several runs on a
project and tell you what the review passes kept catching. `run_findings` gives
it the reviewers' output; `run_activity_errors` gives it what actually broke.
A pattern across runs is a rule you have not written yet.

> Look at the last ten runs on this project. What did the review steps keep
> fixing, and what should go in CLAUDE.md so they stop having to?

Then write the rule, in the same session, in the repository you are already in.
Every later run reads it. That loop is the difference between output that stays
flat and output that gets better, and MCP is what makes it cheap enough to
actually do.

The same applies to workflows. A step that fails often does not need a better
prompt as much as it needs a gate before it, and the run history is what tells
you which.

## Connecting

**Settings → Editor connection** builds the configuration for you: the endpoint,
the key, and a ready-to-paste snippet for Claude Code, Cursor, VS Code and
Claude Desktop.

The key is generated by the server on first start and stored encrypted, so there
is nothing to put in a deployment manifest.

```bash
claude mcp add --transport http harness https://harness.example.com/mcp \
  --header "Authorization: Bearer <your MCP key>"
```

Or for an editor that reads a config file:

```json
{
  "mcpServers": {
    "harness": {
      "type": "http",
      "url": "https://harness.example.com/mcp",
      "headers": { "Authorization": "Bearer <your MCP key>" }
    }
  }
}
```

<Callout type="warn">
Keep the key out of a project's `.mcp.json`. That file is normally committed and
this configuration carries a secret. Use the `claude mcp add` command above,
which writes to your user configuration, or your editor's user-level config.
Keys are prefixed `hrn_mcp_` so secret scanners can catch one that slips into a
repository.
</Callout>

With sign-in enabled, mint a **personal access token** on that page instead of
using the shared key. A run triggered from your editor is then attributed to
you, and revoking one person's access does not disturb anybody else's.

## Two transports

| | **HTTP endpoint** | **`harness mcp-server`** |
| --- | --- | --- |
| How | the running server, at `/mcp` | the binary locally, over stdio |
| Tools | authoring, runs and Linear | authoring only |
| Auth | MCP key or personal access token | `HARNESS_TOKEN` in the client's env |
| Needs | network reach to the harness | the binary on your machine |

Use the HTTP endpoint. The stdio mode exists for clients that cannot do
authenticated HTTP MCP, and it proxies only the `workflow_*` tools, so it can
write workflows but cannot show you a run.

```json
{
  "mcpServers": {
    "harness-authoring": {
      "command": "harness",
      "args": ["mcp-server"],
      "env": {
        "HARNESS_REMOTE_URL": "https://harness.example.com",
        "HARNESS_TOKEN": "<your token>"
      }
    }
  }
}
```

## Tools

### Reading runs

The set you will use most, and the reason to connect this at all.

| Tool | What it does |
| --- | --- |
| `run_status` | One run's progress, node by node |
| `run_node_output` | One step's output (the tail by default) and, if asked, its artifact |
| `run_findings` | What the review passes found |
| `run_activity_errors` | Errors recorded during a run. The first place to look when one fails |
| `run_list` | Recent runs and their states |
| `issue_prs` | Every run for a Linear issue and the PR each opened, with the PR's state, checks and preview link. Answers "which of these two PRs do I test?" |
| `pr_status` | One PR's state, checks and preview link |
| `pr_diff` | What a PR changes: its files and diffs, a file or folder at a time when it is large |

### Authoring workflows

| Tool | What it does |
| --- | --- |
| `workflow_list` | Workflows visible to a project |
| `workflow_get` | One workflow's YAML |
| `workflow_create` | Create a new workflow |
| `workflow_save` | Save a full workflow document |
| `workflow_validate` | Validate without saving |
| `workflow_delete` | Remove a workflow; it stays in the bin for 14 days |
| `workflow_trash` | Deleted workflows that can still be restored |
| `workflow_restore` | Put a deleted workflow back under its own name |
| `workflow_versions` | A workflow's earlier versions; a save keeps the one it replaces |
| `workflow_restore_version` | Make an earlier version current (the replaced one is kept) |
| `workflow_set_node` | Add or update a single node |
| `workflow_remove_node` | Remove a node |
| `workflow_connect` | Wire one node's output into another |
| `workflow_set_ui` | Set the visual editor's layout metadata |
| `workflow_catalog` | The node-type catalog |
| `workflow_models` | Which providers and models are available |

The node-level tools exist so an assistant can edit a workflow incrementally
rather than rewriting the document, and so a malformed edit fails on one node
instead of replacing a working DAG with a broken one. Validate before saving.

### Starting runs

Useful if you are not using Linear, or for the A/B case below.

| Tool | What it does |
| --- | --- |
| `run_trigger` | Start a run: project, workflow, task, optional model override |
| `run_trigger_pair` | Start the **same task twice** on different models |
| `run_linear_claim` | Claim a Linear issue for a run |

### Triggers

The same triggers as the [Triggers page](/docs/triggers#the-triggers-page):
Linear triggers, webhooks and schedules, through one set of tools.

| Tool | What it does |
| --- | --- |
| `trigger_list` | Every trigger: what sets it off, what it starts, and whether it is enabled. Also says which `system` starts Linear runs — `triggers`, or `classic` bindings, in which case Linear triggers are saved but idle. Filter by `kind`, `project` or `workflow` |
| `trigger_save` | Create a trigger, or change one by `id`. Only the fields you give change |
| `trigger_delete` | Delete a trigger by `kind` and `id`. Runs it already started are kept |

A Linear trigger takes `team` and `status` by name (as `linear_states` shows
them) and an optional `label`. It has no status map: the workflow moves the
issue with `linear:` steps. A webhook trigger's `secret` is returned only when
it is created; deliveries go to its `url`. Webhooks and schedules are for
administrators. In the built-in chat, `trigger_save` and `trigger_delete` wait
for you to confirm.

### Improvements

What a workflow's recent runs suggest changing — see
[`improvements:`](/docs/workflows/authoring) in the workflow authoring guide.

| Tool | What it does |
| --- | --- |
| `improvements_list` | Suggestions, filtered by `workflow`, `project` or `status` (new, applied, dismissed), each with the runs that show it. Also how many runs each project has towards its next review |
| `improvements_act` | `review` a workflow's latest runs in a project now; `apply` a repo suggestion, which starts a run that opens a pull request; `dismiss`, `reopen`, or `mark_applied` one you made in the editor |

In the built-in chat, `improvements_act` waits for you to confirm.

### Learned facts and the loop guard

Whether [learned facts](/docs/learned-facts) and the
[loop guard](/docs/loop-guard) are paying off.

| Tool | What it does |
| --- | --- |
| `facts_list` | A project's facts: live, forming and retired. Each one shows how many runs hit its failure before it went live and since, and the recent `learn-facts` runs and how they ended |
| `guard_report` | Each step the loop guard redirected in the last `days` (default 7), and whether that step still hit the same failure afterwards |

### Schedules

The same [schedules](/docs/schedules) as on the Triggers page: workflows that
run at set times with no Linear issue behind them. The trigger tools above
cover these too; these stay for clients that already use them.

| Tool | What it does |
| --- | --- |
| `schedule_list` | Every schedule, with its next run and the last run it started |
| `schedule_preview` | The next five times a cron expression fires in a timezone, or why it's invalid |
| `schedule_create` | Schedule a workflow: project, workflow, cron, timezone, task |
| `schedule_update` | Change a schedule. Only the fields you give change; `enabled: false` pauses it |
| `schedule_delete` | Delete a schedule. The runs it started are kept |
| `schedule_run_now` | Start one run now, without moving the schedule |

Creating, changing, deleting and starting schedules is for administrators,
as on the page. A personal token must be an administrator's; the shared MCP key,
which an administrator issues, may do it too. In the built-in chat each of
these waits for you to confirm.

### Diagnosing Linear

| Tool | What it does |
| --- | --- |
| `linear_states` | The workflow states available in a team |
| `linear_bindings` | Which columns are bound to which workflows |
| `linear_check` | Diagnose a binding. Usually the answer to "why did nothing happen?" |

## Comparing models

`run_trigger_pair` starts one task on two arms with different models, holding
everything else constant. Feed both to
[`judge-ab`](/docs/workflows/bundled#judge-ab) for a verdict scored from the
actual diffs rather than from either model's account of its own work.

This is the one case where triggering from your editor beats the board, because
you are running an experiment rather than doing the work.
