## Project

A registered git repository: a remote, a base branch, and the credentials and
toolchains it needs. Runs always belong to a project, and it is the project that
decides which GitHub account pushes and which Linear workspace an issue can
come from.

A project can span **more than one repository**. Each gets its own folder in the
workspace and `HARNESS_REPOS` tells the agents the layout. That is how a review
can reason about a frontend and the backend where half its logic lives.

## Run

One execution of one workflow against one project. A run owns:

- an isolated **worktree**,
- an **artifacts** directory that outlives it,
- a **cache** directory scoped to the project,
- a record of every node's output, timing and cost.

## Worktree

Every run gets a `git worktree` checked out from the project's base branch, and
throws it away afterwards. Two runs on the same project cannot see each other's
edits, and neither can touch a developer's working copy.

<Callout type="warn">
A worktree comes **from the remote**. It has none of your unpushed local
commits, and there is no local `main` branch inside one, only the remote-tracking
`origin/main`. A step that diffs against a bare `$BASE_BRANCH` quietly falls back
to scanning the whole repository. Diff against `origin/$BASE_BRANCH` instead.
This is the most common authoring mistake there is.
</Callout>

## Workflow

A DAG of nodes, written in YAML or drawn in the visual editor. A name resolves in order from the project's `.harness/workflows/`, then the
server's global directory, then the ones that ship with the harness. A project
can fork a bundled workflow by name without touching the harness.

## Node

One step. A node has a **body** that determines what it does:

| Body | What it is |
| --- | --- |
| `prompt` | An inline AI prompt. |
| `command` | A markdown prompt resolved from `.harness/commands/<name>.md`. |
| `bash` | A shell script. No AI. Its stdout becomes the node's output. |
| `script` | An inline script with an explicit runtime (TS/JS via `bun`, Python via `uv`) and optional dependencies. |
| `loop` | A convergence loop. Repeat until a condition holds. |
| `approval` | A human gate. The run waits. |
| `cancel` | Terminate the run with a reason. |

An AI provider runs `prompt`, `command` and `loop`. `bash` and `script` are
deterministic.

A node also carries `depends_on`, a `when:` condition, a `trigger_rule` for how
it reacts when something it depends on fails, its own `provider`, `model` and
`effort`, `retries`, a `timeout`, an `output_format` schema, and an `artifact` it
produces. [Authoring workflows](/docs/workflows/authoring) covers all of it.

## Provider and model

A **provider** is which agent CLI runs the body. `claude`, `openai-codex`,
`pi` (also accepts `kimi`), or `cursor`. A **model** is which model that agent
uses. Both are per node, so a workflow can plan with an expensive model, write
the code with a cheap one, and have a third review the result. See
[agents and models](/docs/operating/agents).

## Artifacts

A node can declare an `artifact`, a path relative to the run's artifacts
directory such as `exploration.md`. Artifacts outlive the worktree. They are how
a planning step hands a document to the step that implements it, and how you read
back what a run was thinking.

## Toolchains

A project declares which toolchains it needs; `mise` installs them on demand at
run time and caches them on the data volume. Adding a language does not mean
rebuilding the image.

## Trigger

What starts a run. The dashboard, the [MCP endpoint](/docs/mcp), or
[Linear delegation](/docs/integrations/linear). See
[triggering runs](/docs/triggers).
