---
title: "Schedules"
description: "Run a workflow at set times, such as a weekly report, without a Linear issue behind it."
---

Some work has no issue behind it. A report on last week's INP from Grafana, a
Monday sweep of new Sentry errors, a monthly dependency check: you want these
to happen on time, not because someone remembered to ask. A **schedule** runs a
workflow against a project at the times you set.

**Schedules** in the sidebar lists them, with when each one runs next and a
link to the run it last started. Anyone signed in can see the list.
Administrators create, change, pause and delete schedules.

## Creating one

Choose **New schedule** and fill in:

- **Name**, which also titles each run, followed by the date: "Weekly INP
  report — 2026-10-26".
- **Workflow** and **project**, as for any run.
- **When.** Pick a preset, such as *Every Monday at 08:00* or *First of the
  month at 08:00*, or choose **Custom (cron)** and write a five-field cron
  expression (`minute hour day-of-month month day-of-week`). The form shows the
  next few times it will fire, or why the expression is invalid.
- **Timezone**, which defaults to your browser's. Times are read in it, so
  `0 8 * * 1` in `Europe/Copenhagen` stays at 08:00 local time on both sides of
  a daylight-saving change.
- **Task**, the text the run gets as `$ARGUMENTS`, the same as a task typed
  into the dashboard. Say what the run should produce, and for what period.

**Run now** starts a run straight away without moving the schedule. Use it to
try a new schedule out instead of waiting for Monday.

## What a scheduled run is

It is an ordinary run. It appears under **Runs**, its report is on its run
page, and it costs what the workflow costs. The run is credited to the schedule
("Schedule “Weekly INP report”"), not to whoever created it.

There is no issue behind it, so choose a workflow that writes a report rather
than one that opens a pull request. A workflow that reads from
[Sentry](/docs/setup/sentry) or Grafana needs that integration set up first.

## Filing the result in Linear

A report nobody opens is no use. **File the result in Linear** picks a team
from the project's [Linear connection](/docs/setup/linear). Each run that
succeeds then becomes a new issue there, titled like the run, so the team sees
it on their board.

- **The issue body** is the output of the workflow step marked
  `linear_comment: true`, the same short summary a Linear-triggered run posts as
  its comment. Write that step to produce something a person can act on. A
  workflow with no such step files a pointer to the run page instead.
- **It links back** to the run, where the full report is.
- **A failed or cancelled run files nothing.**
- **The issue isn't delegated to the harness.** It is filed for people to read
  and triage. If a finding needs code changed, delegate the issue as usual.

The list shows the issue the latest run became. If Linear is unreachable, the
harness tries again for a few minutes, then gives up on that run. The report
stays on its run page either way.

## When the server was down

A schedule doesn't pile up runs it missed. If the harness is down at 08:00 on
Monday, it starts one run when it comes back, then carries on from the next
occurrence. If several harness instances share a database, each occurrence
still starts only one run.
