A workflow is a DAG of nodes: the pipeline a run executes. You author it in YAML
or draw it in the visual editor, and the harness walks it node by node. It gates
on conditions, passes one node's output to the next, and decides what to do when
a step fails.

## How a workflow is found

A workflow name resolves in order:

1. the project's `.harness/workflows/`,
2. the server's global `.harness/workflows/`,
3. the workflows bundled with the harness.

The first match wins. That is the whole forking story. Copy a bundled workflow
into a project under the same name, change it, and the project's version runs
from then on. Nothing to register, and nothing to un-register when you delete it
again.

## Testing one without spending tokens

`harness run` runs a workflow locally. Without `--real` it uses a built-in echo
agent, so the shape, the gating and the variable wiring all run for free. Check
that a DAG behaves before you pay for it.

```bash
harness run path/to/workflow.yaml --args "a task" --workspace .
```

See the [CLI reference](/docs/operating/cli#harness-run).
