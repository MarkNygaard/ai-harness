These ship with the harness and are ready to run. More are installable from
the [workflow library](/docs/workflows/library). To change one, copy it into
the project's `.harness/workflows/` under the same name. Project workflows
resolve before the bundled defaults, so the fork wins without any registration
step.

<Callout>
This page names vendors rather than model versions, because versions move and
documentation does not. Each workflow pins its actual models in its YAML, which
is the answer if you need to know exactly what runs.
</Callout>

## Task to pull request

### `task`

The default workflow: a Linear issue becomes a reviewed pull request, and the
issue stays up to date as the run goes. Start it from a
[trigger](/docs/triggers) on your "Todo" or "Ready" status, or by hand with a
task description.

The issue's lifecycle is in the workflow itself, as
[`linear:` steps](/docs/triggers#a-trigger-only-starts-the-run):

- The issue moves to In Progress before any tokens are spent.
- The run comments when it picks the issue up, and again with a short plan.
- If validation fails, it says why on the issue.
- The issue moves to In Review once the pull request is open.
- A closing comment links the PR.

Claude explores and plans: a cheap read-only `explore` pass feeds a
`create-plan` pass on a stronger model. Kimi implements, validates and reviews
its own work, and a final build gate runs last. There are no review passes by
other vendors. Run [`review-pr`](#review-pr) on the PR when you want those.

A fresh worktree has no installed dependencies and none of the gitignored
generated files. The `install-deps` step installs them from the lockfile, then
runs the first codegen script it finds (`prebuild`, `codegen`, `generate` or
`db:generate`) in any `package.json` in the repository, not only the root one.
If the root defines the script, only the root's runs. Otherwise pnpm runs it
one package at a time in dependency order, and npm, yarn and bun run it in each
package in turn. The log names the packages that have it, or says none do.

Started by hand, with no issue, every `linear:` step does nothing and the run
behaves like any other. Status names must exist on the issue's team, so rename
`In Progress` and `In Review` in a fork if your board uses other names.

**It also runs epics.** Its first step reads the issue, and a route sends it
one of four ways:

- **An ordinary issue** goes through the pipeline above.
- **An epic** (an issue with sub-issues) is started, not built. The run creates
  the branch `epic/<ID>` and moves the first sub-issue that hasn't begun to
  Todo, where it starts its own run.
- **A piece** (a sub-issue of a started epic) is built on the epic's branch,
  then graded against its own description, with fresh context. If it falls
  short, it gets one round of fixes and a second grade. When it passes, its
  pull request merges into the epic branch, the piece moves to Done, and the
  next piece starts. After the last piece, the epic branch becomes one pull
  request against the default branch, and the epic moves to In Review.
- **An epic whose pieces have all begun** is left alone: there is nothing to
  start.

A piece that fails its grade twice stops. Its pull request stays open, and it
moves to In Review for a person to look at. So does a piece GitHub won't
merge, and the epic gets a comment with GitHub's reason. A piece's pull request
always targets the epic branch, whatever the repository's own docs name as the
base. One Todo trigger runs the whole
thing; see [Linear epics](/docs/setup/linear-epics).

## Working on an existing PR

### `revise-task`

Address reviewer feedback on an existing pull request and push updates. No new
PR is opened. It is the companion to `task`: start it from a trigger on your
"Changes requested" status.

The run finds the PR and gathers the feedback that is new since the last
revision: GitHub reviews and inline comments, and Linear comments written by
people. It checks the PR's branch out, installs its dependencies the same way
`task` does, then explores, plans, implements and validates. Kimi reviews its
own work, then two review-and-fix passes run on other vendors' models, an
OpenAI model and then Claude. A final validate follows. The run replies to the
reviewers in their own threads and posts a summary comment on the PR.

The issue's lifecycle is in the workflow, as `linear:` steps:

- Once real feedback is found, the issue moves to In Progress, and a comment
  lists what will be addressed.
- If validation fails, it says why on the issue.
- The issue moves to In Review when the revision is pushed, and a closing
  comment follows.
- If a step fails, the run says so on the issue.

**No feedback, no move.** With no open PR, or no new feedback, the issue is not
moved. A comment explains why and the run ends cancelled. This guards against a
card moved to "Changes requested" by mistake. To run it again, move the card
out of that status and back.

Only person-written Linear comments count as feedback. The harness's own
comments (plans, summaries, triage notes) reach the run marked `[harness]` and
are ignored, whatever name the Linear app shows. Only comments newer than the
harness's most recent one count, so a second revision does not redo the first.

An epic moved to "Changes requested" has its final pull request (`epic/<ID>`
against the default branch) revised like any other.

Started by hand, with no issue, every `linear:` step does nothing. Rename
`In Progress` and `In Review` in a fork if your board uses other names.

### `review-pr`

Review an existing pull request and fix what is concretely wrong with it: a
simplify pass over the changed files, then two review-and-fix passes on
different vendors' frontier models. Commits go to the PR's own branch, and one
summary comment collects what was fixed and what was flagged. `$ARGUMENTS`
names the PR as a number, a URL, or a Linear issue whose linked PR to review.
After checking the branch out, it installs dependencies the same way `task`
does.

Unlike `revise-task`, it needs no human feedback to act on — it produces the
review rather than addressing one.

**It has no planning step, deliberately.** The PR was not planned here, so
there is nothing to review it against but the code and the author's stated
intent. Scope comes from git: the changed-file set is computed once per repo
against that repo's base branch, and any repo the run had no business touching
is reverted. Intent is recorded from the PR body, its linked issue and its
commits — as claims to verify, not as a contract. Where the diff and the
description disagree, that is reported rather than quietly fixed.

<Callout type="warn">
It pushes to the PR's branch, so a pull request from a fork the harness cannot
push to will fail once a reviewer finds something. Both passes are told to fix
only defects *inside* the diff and to flag anything else for a human — with no
plan there is no record of what the author deliberately left out, so an
"omission" may be their decision. For an assessment that changes nothing, use
[`review-area`](/docs/workflows/library#review-area).
</Callout>

### `task-merge`

Merge the pull request of a Linear issue that is ready to merge. It is the
companion to `task`: start it from a trigger on your "Ready for merge" status.
`$ARGUMENTS` names the PR as a number, a URL, or a Linear issue whose linked
PR should be merged.

It checks the PR's review before anything else:

- **No approved review yet** (a review is still required, or changes were
  requested): nothing is merged and the run does not fail. The issue moves back
  to In Review, with a comment saying why.
- **Approved, or the repository requires no review:** the PR is brought up to
  date, conflicts are resolved if there are any, CI is waited on, and the PR is
  squash-merged. The issue then moves to Done.

If GitHub refuses the merge for another reason, such as a red check, the run
says so on the issue and ends cancelled, leaving the issue where it is. The
review check is a [route node](/docs/workflows/authoring#node-bodies), so the
decision is a rule rather than a model's judgement. Project rules about merge
strategy and verification live in the project's `CLAUDE.md` / `AGENTS.md` and
are loaded into every agent's context automatically. Rename `In Review` and
`Done` in a fork if your board uses other names.

## Review and analysis

### `architect`

A behaviour-preserving codebase-health sweep. Measures stack-aware health
metrics, does a read-only architectural assessment, produces a tightly scoped
plan (no more than five to seven files, KISS/YAGNI/Rule-of-Three), applies hook-enforced
simplification with per-edit verification, then runs a model-diverse
behaviour-preservation review that **reverts any change that drifted
semantics**.

If the sweep finds nothing worth changing, no PR is opened at all.

### `judge-ab`

A pairwise quality judge for A/B model comparisons. Given a shared task and two
arms' results, it decides which did better and scores each out of 100.

When an arm produced a PR it reads the actual diff and judges primarily on the
code, falling back to textual evidence when there is no PR. The judge model is
held constant across the comparison. It then does a second analysis: how much
did the shared late-stage reviewers shape each arm?

Pair it with `run_trigger_pair` over [MCP](/docs/mcp).

## Epics

### `linear-epic-supervise`

Grades a merged epic piece against its own acceptance criteria, then advances
the next one, or files a corrective.

[`task`](#task) runs epics in its own graph, so the usual setup does not need
this, and nothing wires it up for you. It is there for a custom setup in which
separate workflows build and merge the pieces. Bind it to the column a piece
lands in once its PR is merged. It reads the sub-issue's acceptance criteria,
judges the code now on the base branch, and does one of three things: start the
next piece, file a corrective sub-issue, or stop and ask for a human.

**The verdict is the gate.** A piece that was built but built wrong does not
advance the epic, because everything after it is written against what it was
supposed to do.

## Bundled commands

Workflows reference reusable markdown prompts by name through a `command:`
body. These ship alongside the workflows and resolve the same way. A project's
`.harness/commands/<name>.md` shadows the bundled one:

`confirm-plan`, `finalize-pr`, `implement-tasks`, `plan-setup`, `validate`.
