description: "How work reaches the harness. Linear delegation is the full experience; the dashboard and the MCP endpoint cover the cases it does not."

Work can reach the harness several ways, but they are not equivalent, and it is
worth saying which one to reach for.

## Linear, if you can

**Delegate the issue.** The harness registers as a Linear agent: assign an issue
to it or @-mention it, and it picks the work up, walks the issue through a
status map you configure, and reports progress inside the issue's own thread.

This is the full experience, and not because of the integration. It is because
of who it lets drive. An issue is something anyone on the team can write,
including the people closest to the problem and furthest from the codebase. A
board is a queue, a status map is a pipeline, and the thread is where the run
explains itself. Nothing else here gives you that.

A **column poller** also runs for stage-to-stage pipelines, gated per binding by
`live`. Move a card into a bound column and its workflow starts, which is how
review and merge stages chain together without anyone re-delegating.

See [connecting Linear](/docs/setup/linear), and
[Linear epics](/docs/setup/linear-epics) for issues with sub-issues.

## The dashboard

Pick a project, pick a workflow, describe the task, start it. The run page then
shows the DAG executing node by node with each node output, duration and cost.

Right for a one-off, and for watching a run closely while you are still working
out whether a workflow behaves.

## MCP, if you are not using Linear

An assistant connected to the [MCP endpoint](/docs/mcp) can start a run with
`run_trigger`. Reach for it when your work does not live in Linear, or when you
are running an A/B comparison rather than shipping something.

Worth being clear about the emphasis: **triggering is the smallest part of what
the MCP endpoint is for.** Its real use is authoring workflows and reading what
runs actually did, which is a developer's job rather than a requester's. See
[the MCP endpoint](/docs/mcp).

## A schedule, for work with no issue

A weekly report or a nightly check has nobody to ask for it.
[Schedules](/docs/schedules) start a workflow at times you set.

## The Triggers page

Everything that starts a run *by itself* is a **trigger**. **Triggers** in the
sidebar lists every one of them in one list, whatever its kind:

- **Linear** — an issue enters a status in a team and is delegated to the
  harness, or carries a label you name.
- **Webhook** — another service calls the trigger's URL: GitHub, Sentry, a
  deploy pipeline, anything that can send a signed request.
- **Schedule** — a time comes round. See [schedules](/docs/schedules).

Each row says what sets it off, which workflow it starts in which project, when
it last fired, and whether it is **on**, **off** or **idle** (below). Filter by
kind, project or workflow, or search; **New trigger** asks which kind first.

### A trigger only starts the run

This is the difference from a classic [binding](/docs/setup/bindings). A
binding also moves the issue: to In Progress when it claims it, to In Review
when the pull request opens, to Ready when the run completes, back on failure.
A Linear trigger does none of that. It starts the workflow, and the workflow
moves the issue with its own `linear:` steps, next to the work that justifies
each move:

```yaml
nodes:
  - id: start
    linear: { move_state: In Progress }
  # … plan, implement, open the PR …
  - id: in-review
    depends_on: [open-pr]
    linear: { move_state: In Review }
```

The bundled [`task`](/docs/workflows/bundled#task) and
[`task-merge`](/docs/workflows/bundled#task-merge) workflows are written this
way. Trigger `task` on your ready-to-start status and `task-merge` on your
ready-to-merge status.

There is no failed label on the trigger either. A workflow that should label
its issue when a run fails ends with a `linear:` step using
`trigger_rule: one_failed`, which runs only when a step before it failed — see
[handling a failure](/docs/workflows/authoring).

### One trigger per status

A Linear status can start only one workflow. Saving a second Linear trigger
on the same team and status is refused, because both would start a run on
every issue that arrives there. That holds whichever harness project each one
targets and whatever label it adds. The one exception is two triggers narrowed
to different Linear projects, since those never see the same issue.

To do different things for different issues, keep the one trigger and let its
workflow decide with a [route node](/docs/workflows/authoring#node-bodies). For
example, a rule on the issue's labels or a short prompt can send epics to one
set of steps and single tasks to another.

If two triggers on the same status were saved before this rule existed, the
older one fires. The newer one is marked *held back* until one of the two is
removed.

A Linear trigger fires **once each time an issue comes to match it**. While the
issue stays in the status it doesn't fire again; move it out and back (or
un-delegate and delegate it) to run it again. Delegating always starts a run
straight away; the poller catches anything delegation missed, once a minute.

### Classic bindings or Linear triggers

Both read the same issues, so only one of them starts Linear runs.
**Settings → General → Linear triggers** chooses which, for the whole harness.
The default is **project bindings (classic)**, so nothing changes until you
switch. Until then, Linear triggers on this page show as **idle**; after it,
the bindings on each project's Linear tab do. Nothing is deleted either way, so
switching back picks up where it left off.

To move over: create the Linear triggers you need, add `linear:` steps to the
workflows that should move their issue, then switch.

### Webhooks

A webhook trigger gets its own URL, `https://<harness>/api/hooks/<id>`, and a
secret, shown once when the trigger is made (and again only by replacing it).
Deliveries prove they know the secret one of two ways:

- **Signature** (the default): an HMAC-SHA256 of the body with the secret, sent
  as `X-Hub-Signature-256: sha256=<hex>`. This is exactly what GitHub sends, so
  for GitHub paste the URL and secret into the repository's webhook settings
  with content type `application/json`.
- **Token**, for senders that can't sign: the secret as
  `Authorization: Bearer <secret>`, an `X-Harness-Token` header, or
  `?token=<secret>`.

**Only when** conditions narrow what starts a run: each names a path into the
delivery — `body.action`, `headers.x-github-event` — and the values that count.
A delivery that doesn't match is acknowledged and ignored, so the sender
doesn't retry it. A retry of the same delivery (same `X-GitHub-Delivery`,
`X-Request-Id` or a header you name) starts nothing.

The **task** is what the run is asked to do, with parts of the delivery filled
in: `Review {{body.pull_request.html_url}}`. Left empty, the run gets the whole
payload.

Webhooks work whichever system starts Linear runs. Only administrators create
or change them, since each one is a public endpoint.

### Over MCP

An assistant connected over [MCP](/docs/mcp#triggers) can list, create, change
and delete triggers of every kind with `trigger_list`, `trigger_save` and
`trigger_delete`.

## What a trigger supplies

Whichever route it takes, a trigger names the same things:

- the **project** to run against,
- the **workflow** to run,
- free-form text exposed to the workflow as `$ARGUMENTS` and `$USER_MESSAGE`,
- optionally a **model override**, which is how an A/B comparison holds
  everything else still.

## Who a run belongs to

Every run records who set it in motion, whichever route it arrived by.

- **From the UI or MCP** — the signed-in person, or the account behind the
  personal access token.
- **From a Linear delegation** — the person who delegated. Linear makes whoever
  delegates an issue its assignee, so that is who gets the credit.
- **From the poller** — the last person to move the issue into the column the
  binding watches. Not the assignee: an issue delegated by one person and later
  dragged into a re-run column by someone else is a second run, asked for by the
  second person. The harness's own status moves are excluded, so it never
  credits itself for putting an issue back.

A run carries three fields: `trigger_source` (which door it came in through),
`trigger_actor` (the person, as a human reads them) and `triggered_by` (their
harness account id). The last is empty for a colleague who works only in Linear
and has no account here — `trigger_actor` still names them.

A Linear person is matched to an account by their
[linked Linear account](/docs/setup/linear#link-your-linear-account) first, then
by email. Once matched, the run carries the account's name, so the same person
reads the same on a run from Linear as on one from the dashboard.
