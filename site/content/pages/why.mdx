The most reasonable objection to all of this is short: **I can already run a
coding agent in a loop. Why do I need a pipeline?**

Often you don't. This page is the honest version of the answer, including the
cases where you should close this tab and go write a shell script.

## Where this sits

Software delivery has been automated from the outside in.

The usual stages run **Plan, Code, Build, Test, Release, Deploy, Operate.**
Continuous integration automated Build and Test. Continuous delivery automated
Release and Deploy. Over about fifteen years, everything to the right of the
commit got a pipeline: defined as code, triggered by an event, run in an
isolated environment, gated on checks that can fail it.

**Code is the stage nobody automated.** It stayed manual because it was the part
that needed a person.

That is the part that changed. So:

> CI/CD starts at the commit. This starts at the ticket.

Same shape, one stage to the left. Triggered by an event, defined as code in the
repository, run in an isolated environment, gated on checks that can fail it.
The artifact at the end is a pull request rather than a build.

## When a loop is enough

A loop is the right tool more often than vendors admit. Use one when:

- **You are the only person who will run it.** A loop lives in your terminal.
- **The task is small enough to hold in one head.** A rename, a missing null
  check, a test you already know how to write.
- **You will read every line of the diff anyway.** Then most of what a pipeline
  adds is redundant, because you are the gate.
- **You are exploring.** When you do not yet know what you want, a conversation
  beats a specification, and a pipeline needs a specification to start.

If all four are true, a pipeline is overhead. Run the loop.

## What breaks when you scale a loop

The four conditions above stop holding in a specific order, and each failure has
a mechanism behind it rather than a missing feature.

### A model grades its own work generously

Ask an agent to review what it just wrote and it will usually approve it. This
is structural, not a prompting problem: the reasoning that produced the code is
the reasoning being asked to judge it, and it has no reason to disagree with
itself.

The fix is not a better review prompt. It is **a different model doing the
review**. In `idea-to-pr`, Claude plans, Kimi writes the code, then gpt-5.x and
Claude Sonnet each review and fix in turn. None of the reviewers wrote the code.
That is why the pipeline pays for three passes instead of looping the author.

### A loop runs in your working copy

Two tasks cannot run at once. A half-finished edit sits in your tree while you
try to do something else. A bad run leaves you cleaning up.

Every run here gets its own git worktree off the base branch, and throws it away
afterwards. Runs cannot see each other and cannot touch anyone's checkout.

### A loop stops when the model says it is done

There is no build that must pass. The agent decides it has finished, and it is
the same agent whose work you are trying to check.

A build gate written as a node in the DAG cannot be skipped by an agent that
believes it is finished. Neither can a review pass. The pipeline decides what
runs next, not the model.

### Nothing is written down

When a loop produces something wrong, you get the final state and a scrollback
buffer. You cannot see which step went wrong, what it cost, or why it chose that
approach.

Every node's output, duration and cost is recorded. A run you can inspect is a
run you can improve.

### A loop cannot be handed to anyone else

This is the one that matters most, and it is not a technical limitation.

A loop needs a terminal, an API key and someone who can read a diff. The person
in your company who knows exactly what the checkout page should do, and who
would test it properly, cannot run one.

A pipeline that triggers from a ticket can be handed to that person. See
[shipping without writing code](/docs/shipping-without-code). That is not a
convenience feature. It changes who is allowed to build software, which is a
different claim from "the agent writes code faster".

### Standards have to be repeated

In a loop, every conversation starts from nothing. You re-explain the merge
policy, the verify commands, the module that owns the thing you are touching.

The [`AGENTS.md` and `CLAUDE.md` cascade](/docs/project-rules) is loaded into
every run automatically. Write the rule once and every future run has it. Review
effort falls over time instead of staying flat.

## What this does not fix

Worth being explicit, because the limits are real.

**A bad agent stays bad.** The harness writes prompts and runs the pipeline. It
has no opinion about the code. Better isolation and more review passes catch
more mistakes, but nothing here makes a weak model write good software.

**A vague ticket produces a confident wrong answer.** The system will resolve
your ambiguity for you and will not tell you it did. Specification is still the
hard part, and it is still yours.

**Nothing here forces a human to review.** The bundled workflows stop at a pull
request, but that is a default, not a constraint. Bind
[`merge-pr`](/docs/workflows/bundled#merge-pr) to a column, have `idea-to-pr`
move the issue there when it finishes, and the chain runs from ticket to merged
with nobody in it. What `merge-pr` waits for is CI passing, not an approval.

If you want review enforced, that is branch protection on the repository, and it
is worth turning on. The harness gives you a good place to put a human. It does
not check that you did.

**More passes cost more.** Three review passes cost roughly three review passes.
The trade is money against defects reaching a human, and for a small change that
trade is often bad.

## Why this rhymes with CI

Continuous integration was not adopted because pipelines were clever. Teams
adopted it because integrating in big manual batches stopped working once there
was more than one developer, and the failure was expensive and late.

Running an agent in a loop works the same way. It is fine until there is more
than one task, more than one person, or someone involved who cannot read the
diff. Then the thing that breaks is not the agent. It is everything around it.

That is the part this builds.
